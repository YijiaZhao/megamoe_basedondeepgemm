# SM120 MegaMoE: W4A4 (MXFP4 / NVFP4) and W4A8

W4A4 (MXFP4, NVFP4) and W4A8 (MXFP4 weights x MXFP8 activations) on one kernel:

| File | What |
|---|---|
| `deep_gemm/include/deep_gemm/impls/sm120_fp4_mega_moe.cu` | kernel + torch extension, one build per format (`SM120_FP4_NV`, `SM120_FP4_A8`) and transport (`SM120_FP4_GIN`) |
| `deep_gemm/include/deep_gemm/impls/sm120_fp4_mega_moe_gin.cu` | NIC transport session (host only): NCCL window, peer pointers, GIN device communicator |
| `deep_gemm/mega/sm120_fp4.py` | `Sm120Fp4MegaMoeBuffer`, `fp4_mega_moe_sm120`, `transform_fp4_weights_for_mega_moe_sm120`, `nvfp4_global_scales` |
| `tests/test_mega_moe_sm120_fp4.py` | correctness (`verify`), timing (`bench`) |
| [`ENV.md`](ENV.md) | the environment variables it reads (none is needed; none changes the kernel) |

EP over PCIe P2P (or the NIC, see Transport), one persistent kernel per rank, no cross-rank barrier. The dispatch and the FC1 epilogue quantize
the activations; FC1 / FC2 run swap-AB `mma.sync`:

| Format | Weights and activations | MMA |
|---|---|---|
| `mxfp4` | E2M1, UE8M0 scale per 32 | `kind::mxf4nvf4` m16n8k64 `scale_vec::2X` |
| `w4a8` | weights E2M1, activations E4M3, UE8M0 scale per 32 | `kind::mxf8f6f4` m16n8k32 `scale_vec::1X`, two per K64 |
| `nvfp4` | E2M1, UE4M3 scale per 16, fp32 global scales: per expert for W13 / W2 (`weight_scale_2`), per tensor for the FC1 / FC2 inputs (`input_scale`, the same on every rank) | `kind::mxf4nvf4` m16n8k64 `scale_vec::4X` |

```python
from deep_gemm.mega import sm120_fp4
l1, l2 = sm120_fp4.transform_fp4_weights_for_mega_moe_sm120((w13, w13_sf), (w2, w2_sf), 'nvfp4')
gs = sm120_fp4.nvfp4_global_scales(fc1_input_scale, fc2_input_scale, w13_scale_2, w2_scale_2)  # nvfp4 only
buf = sm120_fp4.Sm120Fp4MegaMoeBuffer(group, 'nvfp4', num_experts, max_tokens_per_rank, top_k, hidden, inter)
sm120_fp4.fp4_mega_moe_sm120(y, x, topk_ids, topk_weights, l1, l2, buf, gs, activation_clamp=limit)
```

```bash
torchrun --nproc-per-node 8 tests/test_mega_moe_sm120_fp4.py verify mxfp4    # or nvfp4 / w4a8
torchrun --nproc-per-node 8 tests/test_mega_moe_sm120_fp4.py bench nvfp4 2 4 8 16 64 256 512   # or mxfp4 / w4a8
```

## Results (2026-11-10, 10.6.142.20, 8x RTX 6000D)

Correctness, against a reference that applies the kernel's quantization (activations and SwiGLU output), max relative L2
over ranks, EP8: small shape (H 512 / I 256, 128 experts, top-6, T 1-64 with padding tokens) 1.73e-3 MXFP4 / 1.79e-3
NVFP4 / 1.74e-3 W4A8; README shape 1.69e-3 MXFP4 / 1.71e-3 W4A8 / 6.57e-3 NVFP4 (the NVFP4 value comes from the single-token case; likely the
coarser UE4M3 scales of the FC2 input, not checked further); wide shape (H 5120 / I 256, 128 experts, top-6: the
dispatch sends each token in several shared-memory chunks) 1.69e-3 MXFP4 / 1.72e-3 NVFP4 / 1.71e-3 W4A8.

Timing: README shape (`bench`): E384 (48 per rank) / H3072 / I1280 / top-8, EP8, global M tokens, balanced routing,
kernel time on GPU 0, µs, cold L2: in serving other layers run between two calls of one layer, so its weights are not
in L2. Before each replay 256 MB of other data are written (the H20 / B200 tables' flush), ranks released by a
barrier; median of 30 replays.

| M | `w4a8` | `mxfp4` | `nvfp4` |
|---:|---:|---:|---:|
| 2 | 43.6 | 43.8 | 46.8 |
| 4 | 57.7 | 57.2 | 60.8 |
| 8 | 78.6 | 78.4 | 81.3 |
| 16 | 116.3 | 115.0 | 120.8 |
| 64 | 266.2 | 265.3 | 277.6 |
| 256 | 273.3 | 272.3 | 285.1 |
| 512 | 292.0 | 277.2 | 291.4 |

Floor: cold time is the read of the active experts' weights from DRAM (5.98 MiB per MXFP4 expert) plus ≈ 10 µs before
the first read (routing) and ≈ 15-20 µs after the last (FC2 tail, combine). `w4a8` stamps: M8 reads 48 MB between 9
and 50 µs, M64 all 48 experts (292 MB) between 16 and 245 µs, ≈ 1.2 TB/s; from M48 on all 48 experts are active. M512 of `w4a8` is bound by compute (two m16n8k32 MMAs per K64 instead of one m16n8k64).

What the time goes to and what the kernel does about it:

* Work order: each tile's FC2 items follow its FC1 items after `lag` tiles (FC1 of tile t + lag, then FC2 of tile t),
  so the partials go back over PCIe during the weight stream, not after it.
* Routing: each rank sends every peer its 48 per-expert token counts first; the owners build the expert map from
  them before the token rows land.
* Cross-rank flags: one CTA polls the PCIe-written flags and republishes them on a local word, so the other
  311 CTAs do not read over PCIe. Flags are plain stores after `__threadfence_system`.
* Weight loads: streaming loads (`__ldcs`, evict-first): every call reads the weights from DRAM, and they need not
  stay in L2. With 8 tokens per item (one MMA per weight fragment) the GEMM loop is double-buffered: the next step's
  weights and scales are loaded while this step's MMAs run; with 16 the loop is unrolled twice instead.
* L2 prefetch: at t=0 the CTAs that do not dispatch pull the locally known experts' FC1 weights (up to 64 MB); after
  the expert map each CTA pulls its static first item's weights (when there are more than 8 tiles).
* Tokens per work item (`tile_tokens`): 8 or 16; each weight fragment feeds that many tokens. Default, every format:
  8 while the expected tokens per local expert are at most 8, else 16.

NVFP4 is slower than MXFP4 because its weights carry twice the scale bytes (one E4M3 per 16 values).

## Transport

`Sm120Fp4MegaMoeBuffer(..., transport=)`, up to 16 ranks:

| `transport` | Buffer | Peers |
|---|---|---|
| `'p2p'` (default) | one `cudaMalloc`, shared over `cudaIpc` | every peer over PCIe P2P stores |
| `'auto'` | one NCCL symmetric window | the peers NCCL maps for load/store (same host) over P2P, the others (another host) over the NIC |
| `'nic'` | one NCCL symmetric window | every other rank over the NIC |

NIC peers get NCCL GIN puts (NCCL Device API, from inside the kernel): the payload is staged in this rank's window,
then put to the peer's window at the offset a P2P store would use. Each put adds 1 to a signal of the receiver (one
per source and kind), and the receiver waits for the number of puts it expects: 1 for the routing counts, 3 per token
row (values, scales, metadata), 1 per token and FC2 item for the partials. `'auto'` / `'nic'` need a ProcessGroupNCCL
group and NCCL 2.30.7 with the Device API (the `nvidia-nccl` wheel); call `buffer.destroy()` before the process group
is destroyed. On a host whose NICs cannot reach each other, pin one NIC: `NCCL_IB_HCA==mlx5_0` ([`ENV.md`](ENV.md)).

Correctness over the NIC, EP8 on .20 (every other rank over GIN, `'nic'`): the same errors as P2P for every format and
shape above; also with the two CPU sockets' GPUs reaching each other over the NIC and P2P within a socket.

Timing on .20, MXFP4, EP8, cold L2 as above, µs. All ranks share one NIC (`mlx5_0`, next to GPUs 0-1): this host's NICs
sit on different subnets. The partials go back as one 256 B put per token and FC2 item, not yet packed per tile.

| M | `'p2p'` | `'auto'` (all pairs P2P) | NIC across sockets, P2P within | `'nic'` |
|---:|---:|---:|---:|---:|
| 2 | 43.8 | 51.3 | 103.5 | 117.3 |
| 16 | 116.3 | 122.8 | 225.9 | 296.0 |
| 512 | 276.6 | 280.1 | 3023.2 | 5069.7 |

`'auto'` is slower than `'p2p'` with the same P2P pairs: the NCCL window memory (`ncclMemAlloc`) instead of
`cudaMalloc` + `cudaIpc`; not yet understood. One pair of this host (NCCL send / recv, 64 MB): 50.5 GB/s P2P within a
CPU socket, 45.9 GB/s P2P across the sockets, 27.7 GB/s across the sockets over `mlx5_0`; within a host P2P is the
faster path here.
