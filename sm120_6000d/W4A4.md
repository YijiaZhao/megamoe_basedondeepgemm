# SM120 MegaMoE: W4A4 (MXFP4 / NVFP4) and W4A8

W4A4 (MXFP4, NVFP4) and W4A8 (MXFP4 weights x MXFP8 activations) on one kernel:

| File | What |
|---|---|
| `deep_gemm/include/deep_gemm/impls/sm120_fp4_mega_moe.cu` | kernel + torch extension, one build per format (`SM120_FP4_NV`, `SM120_FP4_A8`) and transport (`SM120_FP4_GIN`) |
| `deep_gemm/include/deep_gemm/impls/sm120_fp4_mega_moe_gin.cu` | NIC transport session (host only): NCCL window, peer pointers, GIN device communicator |
| `deep_gemm/mega/sm120_fp4.py` | `Sm120Fp4MegaMoeBuffer`, `fp4_mega_moe_sm120`, `transform_fp4_weights_for_mega_moe_sm120`, `nvfp4_global_scales` |
| `tests/test_mega_moe_sm120_fp4.py` | correctness (`verify`), timing (`bench`) |
| [`ENV.md`](ENV.md) | the environment variables it reads (none is needed; none changes the kernel) |

EP over PCIe P2P (or the NIC, see Transport), one persistent kernel per rank, no cross-rank barrier. The dispatch and the FC1 epilogue quantize
the activations; FC1 / FC2 run swap-AB `mma.sync`:

| Format | Weights and activations | MMA |
|---|---|---|
| `mxfp4` | E2M1, UE8M0 scale per 32 | `kind::mxf4nvf4` m16n8k64 `scale_vec::2X` |
| `w4a8` | weights E2M1, activations E4M3, UE8M0 scale per 32 | `kind::mxf8f6f4` m16n8k32 `scale_vec::1X`, two per K64 |
| `nvfp4` | E2M1, UE4M3 scale per 16, fp32 global scales: per expert for W13 / W2 (`weight_scale_2`), per tensor for the FC1 / FC2 inputs (`input_scale`, the same on every rank) | `kind::mxf4nvf4` m16n8k64 `scale_vec::4X` |

```python
from deep_gemm.mega import sm120_fp4

```

### What changed (W4A4 only; W4A8 runs as before)

* Activation layout: the staged token rows and the FC1 output store each K256 block's 32 words in the order the GEMM
  lane reads them (word kc * 8 + h * 4 + c of the MMA order at c * 8 + kc * 2 + h), so one K256 step of a lane's
  sub-tile is two 16 B loads plus one scale load instead of eight 4 B loads plus four. The quantization writes the rows
  anyway; nothing is moved twice. This is most of the gain at 128+ tokens per rank, where each weight fragment feeds
  several 8-token sub-tiles.
* 32- and 64-token work items: each weight fragment feeds 4 / 8 sub-tiles, so an expert's weights pass through L2
  fewer times. The 64-token build runs one CTA per SM (255 registers: at 128 the accumulators and the step's
  activations spill); its `s_tile` (32 KB) is dynamic shared memory.
* Tokens per item, `tile_tokens=0`, from the expected tokens per local expert e = T * top-k / local experts: 8 up to
  e 8; then for I >= 2048 16 below e 16, 32 below e 32, 64 from e 32; for smaller I (the README shape) 16 below e 48,
  32 from e 48. From a forced 16 / 32 / 64 sweep (MXFP4, EP8, 128-1024 tokens per rank, the four shapes above):
  experts of I >= 2048 are fastest with wide items early (DeepSeek-V4.1-Flash at 384 tokens per rank: 1363 / 1101 /
  912 µs for 16 / 32 / 64), the I 1280 shape is bound by the weight stream and is fastest at 16 up to e 43 (README
  shape at 192 tokens per rank: 420 / 442 / 445 µs).
* The static first item's L2 prefetch after the expert map runs at any tile count (before: only above 8 tiles): at 1
  token per rank the weights arrive between the expert map and the rows (-3.7 to -5.8 % above).
* `kMaxTiles` 2304 → 16640 (up to 1024 tokens per rank at 16 ranks, top-8, with a NIC peer), and H, I must be
  multiples of 256 (the GEMM loop's K256 steps, which the code already assumed).

What the time goes to and what the kernel does about it:

* Work order: each tile's FC2 items follow its FC1 items after `lag` tiles (FC1 of tile t + lag, then FC2 of tile t),
  so the partials go back over PCIe during the weight stream, not after it.
* Routing: each rank sends every peer its 48 per-expert token counts first; the owners build the expert map from
  them before the token rows land.
* Cross-rank flags: one CTA polls the PCIe-written flags and republishes them on a local word, so the other
  311 CTAs do not read over PCIe. Flags are plain stores after `__threadfence_system`.
* Weight loads: streaming loads (`__ldcs`, evict-first): every call reads the weights from DRAM, and they need not
  stay in L2. With 8 tokens per item (one MMA per weight fragment) the GEMM loop is double-buffered: the next step's
  weights and scales are loaded while this step's MMAs run; with 16 / 32 / 64 the loop is unrolled twice instead.
* L2 prefetch: at t=0 the CTAs that do not dispatch pull the locally known experts' FC1 weights (up to 64 MB); after
  the expert map each CTA pulls its static first item's weights (W4A8: when there are more than 8 tiles).
* Tokens per work item (`tile_tokens`): 8 / 16 / 32 / 64, see above.

NVFP4 is slower than MXFP4 because its weights carry twice the scale bytes (one E4M3 per 16 values).

## Transport

The timing tables of this section and of the EP16 subsection were measured before the 2026-11-25 changes (at or
before 383e53f); the transport comparisons they make do not depend on the GEMM changes above.

`Sm120Fp4MegaMoeBuffer(..., transport=)`, up to 16 ranks. `'p2p'` (default): one `cudaMalloc` shared over `cudaIpc`,
every peer over PCIe P2P stores. Every other value is one NCCL symmetric window plus a per-pair transport table: each
pair of ranks uses P2P stores (LSA) or NCCL GIN puts through the NIC. The tables and their rules are FlashInfer's Cake
SM120 MegaMoE's (`cake_transport.py`), ported to `deep_gemm/mega/sm120_fp4_transport.py`. Which pairs can use P2P at
all is NCCL's peer mapping of the window, not a rule of this code: on the CX8 hosts (.1/.3/.6) NCCL maps only the GPUs
of one CPU socket when `NCCL_IB_HCA` lists all 8 NICs, and every pair with one NIC.

| `transport` | Pairs over P2P |
|---|---|
| `'all_gin'` | none: every other rank over the NIC |
| `'all_lsa'` | all; an error if NCCL does not map a pair |
| `'lsa_where_reachable'` | the pairs NCCL maps (e.g. the same host), the others over the NIC |
| `'auto'` | the table a setup probe picks: it times `all_gin`, `all_lsa`, `lsa_where_reachable` and `lsa_where_faster` (P2P where mapped and its measured pair bandwidth is at least the NIC's) in an all-to-all of one full call's bytes per destination (a token row out, a bf16 partial row back per route, top-k / world routes per token); a mixed table must beat the best uniform one by 3 % and repeat within 1.5×; rank 0 decides |
| `'tuned'` | the table recorded for this deployment (`'auto'` with `DG_SM120_TRANSPORT_RECORD=1` records it, [`ENV.md`](ENV.md)); `all_gin` when none is |
| `(c0, c1, ...)` | an explicit `world × world` table: 0 on the diagonal, 1 P2P, 2 NIC, symmetric |

NIC peers get NCCL GIN puts (NCCL Device API, from inside the kernel): the payload is staged in this rank's window,
then put to the peer's window. The token rows for one peer (values, scales and metadata, one pool row each) are
staged packed in (its local expert, slot) order and go in one put after the whole dispatch, to a receive region the
peer reads by that packed index (one put per row was bound by the NIC's message rate on .3: MXFP4 M1024 1047 µs per
row vs 888 packed); the partials of an FC2 tile go back once all of its FC2 items are done, one put per source rank
with its rows packed the same way. Each put adds its rows to a signal of the receiver
(one per source and kind; 1 for the routing counts), and the receiver waits for the number of rows it expects
instead of a flag. The window transports need a ProcessGroupNCCL
group and NCCL 2.30.7 with the Device API (the `nvidia-nccl` wheel); call `buffer.destroy()` before the process group
is destroyed. On a host whose NICs cannot reach each other, pin one NIC: `NCCL_IB_HCA==mlx5_0` ([`ENV.md`](ENV.md)).

Correctness over the NIC, EP8 on .20 (every other rank over GIN, `'all_gin'`): the same errors as P2P for every format and
shape above; also with the two CPU sockets' GPUs reaching each other over the NIC and P2P within a socket.

P2P across this host's root ports collapses under the all-to-all: one GPU alone writes 30-42 GB/s to any other, but
writes leaving one root port for GPUs behind two or more other root ports at once get ≈ 1.5 GB/s (8-GPU all-to-all:
0.7 GB/s per GPU), hence `'p2p'` / `'all_lsa'` from M16 on. The probe sees it too (one NIC: `all_lsa` 9.9 ms vs
`all_gin` 2.1 ms, 974 KB per destination). With all 8 NICs it timed `lsa_where_reachable` 242 µs vs `all_gin` 243 µs,
inside the 3 % margin, so `'auto'` kept `all_gin`; in the kernel `lsa_where_reachable` is 1-5 % faster. Up to M8 the NIC
tables pay the NIC's latency: each put takes 8-20 µs to post (cold L2) and 15-30 µs to land, and a call waits on two
or three of them in a row (route counts, rows, partials), against 1-2 µs over P2P. With two NICs (`mlx5_0,mlx5_4`)
NCCL maps every pair, but the NIC tables then share two NICs (same-socket P2P / cross-socket NIC, explicit table:
M1024 518 µs).
