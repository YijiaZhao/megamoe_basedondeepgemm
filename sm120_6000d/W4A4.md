# SM120 W4A4 MegaMoE (MXFP4 / NVFP4)

New kernel (W4A4, and W4A8 on the same dataflow) next to the old W4A8 one (`sm120_mxfp4_mega_moe.cu` / `deep_gemm/mega/sm120.py` are unchanged):

| File | What |
|---|---|
| `deep_gemm/include/deep_gemm/impls/sm120_fp4_mega_moe.cu` | kernel + torch extension, one build per format (`SM120_FP4_NV`, `SM120_FP4_A8`) |
| `deep_gemm/mega/sm120_fp4.py` | `Sm120Fp4MegaMoeBuffer`, `fp4_mega_moe_sm120`, `transform_fp4_weights_for_mega_moe_sm120`, `nvfp4_global_scales` |
| `tests/test_mega_moe_sm120_fp4.py` | correctness (`verify`), timing (`bench`; `w4a8_old` runs the old kernel) |

Same dataflow as W4A8 (EP over PCIe P2P, one persistent kernel per rank, no cross-rank barrier); the dispatch and the
FC1 epilogue quantize to FP4 instead of MXFP8, and FC1 / FC2 run `mma.sync kind::mxf4nvf4` m16n8k64 (one MMA per K64):

| Format | Weights and activations | MMA |
|---|---|---|
| `mxfp4` | E2M1, UE8M0 scale per 32 | `scale_vec::2X` |
| `nvfp4` | E2M1, UE4M3 scale per 16, fp32 global scales: per expert for W13 / W2 (`weight_scale_2`), per tensor for the FC1 / FC2 inputs (`input_scale`, the same on every rank) | `scale_vec::4X` |

```python
from deep_gemm.mega import sm120_fp4
l1, l2 = sm120_fp4.transform_fp4_weights_for_mega_moe_sm120((w13, w13_sf), (w2, w2_sf), 'nvfp4')
gs = sm120_fp4.nvfp4_global_scales(fc1_input_scale, fc2_input_scale, w13_scale_2, w2_scale_2)  # nvfp4 only
buf = sm120_fp4.Sm120Fp4MegaMoeBuffer(group, 'nvfp4', num_experts, max_tokens_per_rank, top_k, hidden, inter)
sm120_fp4.fp4_mega_moe_sm120(y, x, topk_ids, topk_weights, l1, l2, buf, gs, activation_clamp=limit)
```

```bash
torchrun --nproc-per-node 8 tests/test_mega_moe_sm120_fp4.py verify mxfp4    # or nvfp4
torchrun --nproc-per-node 8 tests/test_mega_moe_sm120_fp4.py bench nvfp4 2 4 8 16 64 256 512 1024   # or mxfp4 / w4a8 / w4a8_old; COLD=read
```

## Results (2026-11-10, 10.6.142.20, 8x RTX 6000D)

Correctness, against a reference that applies the kernel's quantization (activations and SwiGLU output), max relative L2
over ranks, EP8: small shape (H 512 / I 256, 128 experts, top-6, T 1-64 with padding tokens) 1.73e-3 MXFP4 / 1.79e-3
NVFP4 / 1.74e-3 W4A8; README shape 1.69e-3 MXFP4 / 1.71e-3 W4A8 / 6.57e-3 NVFP4 (the NVFP4 value comes from the single-token case; likely the
coarser UE4M3 scales of the FC2 input, not checked further).

Timing: README shape (`bench`): E384 (48 per rank) / H3072 / I1280 / top-8, EP8, global M tokens, balanced routing,
kernel time on GPU 0, µs. Cold is the number that matters in serving (other layers run between two calls of one layer,
so its weights are not in L2): before each replay L2 is filled with other data by reading 256 MB (`COLD=read`), median
of 30. Warm (back-to-back replays, median of the last 3 of 30, the README headline) is listed second for reference.
`w4a8` is MXFP4 x MXFP8 on this kernel (`SM120_FP4_A8`); `w4a8_old` is the unchanged kernel of `sm120.py`.

With the README cold method (256 MB written, not read, before each replay) the cold values are 9-30 µs higher (`w4a8`
M2-M256: 44.8 / 60.1 / 78.0 / 128.9 / 264.7 / 281.0): written lines left in L2 slow the following reads to
0.83-1.02 TB/s.

Floor: cold time is the read of the active experts' weights from DRAM (5.98 MiB per MXFP4 expert, ≈ 1.24 TB/s) plus
≈ 10 µs before the first read (routing) and ≈ 10 µs after the last (FC2 tail, combine). `w4a8` stamps: M8 reads 48 MB
between 12 and 52 µs, M16 96 MB between 9 and 87 µs, both at 1.2 TB/s; from M48 on all 48 experts are active (292 MB,
≈ 235 µs). M512 / M1024 of `w4a8` are bound by compute (two m16n8k32 MMAs per K64 instead of one m16n8k64).

Tried for cold and dropped: CTAs without a work item (M2 / M4: 224 / 136 of 312) pulling the weights into L2, by
prefetch or by loads: 1-8 µs slower cold, 4 µs slower warm. Always-streaming loads with the first-item prefetch: 3-6 µs
slower at M2 / M4, equal from M8.

What the time goes to and what the kernel does about it:

* Work order: each tile's FC2 items follow its FC1 items after `lag` tiles (FC1 of tile t + lag, then FC2 of tile t),
  so the partials go back over PCIe during the weight stream, not after it.
* Routing: each rank sends every peer its 48 per-expert token counts first; the owners build the expert map from
  them before the token rows land.
* Cross-rank flags: one CTA polls the PCIe-written flags and republishes them on a local word; with all 312 CTAs
  polling, the flags were seen 2-5 µs late. Flags are plain stores after `__threadfence_system`.
* Weight loads per call: if the active experts' weights fit in L2 (≤ 110 MB: MXFP4 up to M16) they are loaded with
  plain loads and stay in L2 for the next call, and the first-item L2 prefetch is skipped; otherwise streaming loads
  (`__ldcs`, ≈ 9% faster than plain once past L2) and the prefetch stays on.
* Tokens per work item (`tile_tokens`): 8-32; each weight fragment feeds up to 4 MMAs.

NVFP4 is slower than MXFP4 because its weights carry twice the scale bytes (one E4M3 per 16 values); at M16 its active
weights (106 MB) are close to the L2 size.
